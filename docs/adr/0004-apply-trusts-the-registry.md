# Apply's outcome comes from re-reading the registry, not from the worker's report

After the Elevated Worker returns, Pending Changes re-reads every exe in the batch and takes that as the result: what stays pending, and which exes become managed (provenance, `ManagedExes`, for Orphaned Override detection). The worker's `ApplyReport` only supplies error text. Reason: the report is unreliable exactly when it matters. A worker that dies mid-batch leaves no `result.json`, which `OpsFile.ReadReportAsync` reports as `BatchRejected` although some ops may have landed; and `PriorityService.Write` can write CPU and then fail on IO, reporting `Success=false` for a value that did change. So an exe is recorded as managed when its re-read value differs from the one before Apply, and a rejected batch is re-read too. User-facing text never claims "nothing was written".
